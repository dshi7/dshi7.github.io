## Nvidia Blackwell GEMM (warp specialization)

I made a diagram to illustrate the data channel of a tile computing matmul between BMxK and KxBN.

NOTE. All the first-principle discussion should be DSL agnostic but [TLX Blackwell GEMM](https://github.com/facebookexperimental/triton/blob/main/third_party/tlx/tutorials/blackwell_gemm_ws.py) contains an excellent example of implementation.

![blackwell gemm data flow](/assets/img/posts/gemm/blackwell_gemm_data_flow.png)

- TMA warp groups: op1 GMEM->SMEM, op2 GMEM->SMEM
- MMA warp group: op1 @ op2 => op3 (TMEM)
- Epilogue warp group: op3 TMEM->RF(downcast)->SMEM->GMEM
- Warp groups communicate with each other with barriers (see the fundamental mental model built in [my another blog](https://dshi7.github.io/posts/barriers/)). Mbarriers live in SMEM.

Here comes the best part: brainstorming "what-if" as below: 

|  | Low | High |
| --- | --- | --- |
| SMEM\\_BUF | Can't hide GMEM->TMEM latency => Stall MMA WG | Suppress SM concurrency (if bottlenecked by SMEM) without getting any benefits |
| TMEM\\_BUF | Can't hide epilogue latency => Stall MMA WG | Suppress SM concurrency (if bottlenecked by TMEM) without getting any benefits |
| EPILOGUE\\_SUBTILE | Register spill by BM\\_S x (BN/EPILOGUE\\_SUBTILE) | Break memory vectorization (BN/EPILOGUE\\_SUBTILE) and choke write-back bandwidth |
| MMA\\_GROUPS | Limits instruction interleaving in the Tensor Core | Harm arithmetic intensity and waste tensor core lanes with micro-math fragments |

- Assume not exceeding SMEM/TMEM cap
- First-principled goals: latency hiding and arithmetic intensity

## AMD MI350x GEMM (warp pipelined)

Preliminaries: hardware primitives

| NVIDIA (Blackwell) | AMD (MI350X) | Note |
| --- | --- | --- |
| Warp | Wave/Wavefront | 32 threads vs 64 threads |
| Tensor Core | Matrix Core | `wgmma` vs `mfma_` (e.g. `v_mfma_f32_32x32x8f16`) |
| SM | CU | same |
| SMEM | LDS<br>(local data share) | - 232KB vs 160KB<br>- No dedicated TMA-like engine. Require active wavefront |
| Registers | VGPR/AGPR<br>(vector/accumulation general purpose registers) | - VGPR for mm operands and AGPR for mm accum<br>- physically unified in CU |

I will use [TLX MI350x warp pipelined GEMM](https://github.com/facebookexperimental/triton/blob/main/third_party/tlx/tutorials/amd_gemm_warp_pipeline.py) to study how it works.

I made another diagram to show the data channel and consumed hardware resources.

![amd gemm warp pipeline](/assets/img/posts/gemm/amd_gemm_warp_pipeline.png)

- Each main for-loop iteration (1) performs MFMA on register operands loaded previously and (2) issues async load (GMEM->LDS) for next iterations
- **HW: Inst dispatch unit handling multiple waves issues instructions in a RR behavior**
- Async load (pushing into async HBM queue) takes much fewer clock cycles than MFMA => interleaving penalty
- **HW: AMD supports adjusting priority of certain assembly code block. Inst dispatcher signaled by higher priority will keep favoring all the instructions from single wave in instruction scheduling until priority is reset.**
- By prioritizing async loads in kernel, MFMA (current iteration) and GMEM->LDS (next round) are actually pipelined.
